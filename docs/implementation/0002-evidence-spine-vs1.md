# Implementation 0002 - Evidence Spine VS1

Date: 2026-09-25  
Status: In progress

## Goal

Prove one end-to-end evidence path before adding a general crawler.

The target flow is:

```text
SourceDefinition
  -> HttpFetcher
  -> SHA-256
  -> content-addressed R2 body
  -> source_snapshots row in Neon
  -> observation
  -> claims
  -> provenance API
```

## Initial source

The first source adapter is intentionally boring:

```text
Teremki@LAN official website
https://www.teremki.net.ua/
```

This is a seed for validating the architecture, not a statement that one source is enough to model the provider.

## Implemented in this slice

- source domain types;
- initial source registry;
- deterministic HTTP fetcher;
- safe response-header allowlist;
- 2 MiB snapshot guard;
- SHA-256 body hashing;
- content-addressed R2 object naming;
- R2 physical-body deduplication;
- source collection composition;
- read-only source registry API;
- first PostgreSQL Evidence Spine migration.

## R2 object layout

Physical bodies are content addressed:

```text
sha256/<first-two-hex>/<full-sha256>
```

Repeated identical responses may share one physical R2 object.

This does **not** collapse logical fetch history.

Each fetch still becomes its own `source_snapshots` row in PostgreSQL once Neon is connected.

## Why the collector is not public yet

There is deliberately no unauthenticated endpoint that causes Netco to fetch arbitrary URLs.

That would create:

- SSRF risk;
- abuse/cost risk;
- accidental load on third-party provider sites;
- a path around the Source registry.

Collection will first be invoked by a controlled internal workflow/scheduler.

## Database migration

`db/migrations/0001_evidence_spine.sql` creates:

```text
sources
subjects
entities
entity_names
source_snapshots
observations
claims
```

UUIDs are generated by application code.

The migration does not depend on a PostgreSQL UUID extension.
