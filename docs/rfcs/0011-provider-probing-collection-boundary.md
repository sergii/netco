# RFC 0011 - Provider Probing and Collection Boundary

Date: 2026-09-25
Status: Draft

## Context

Netco may eventually provide a highly useful discovery product for Ukraine:

    address
      -> available internet providers
      -> technology
      -> freshness
      -> evidence

This can be especially valuable when users need to understand connectivity options under unstable power and network conditions.

At the same time, provider coverage data may be operationally or commercially sensitive. A provider may not want automated systems to enumerate its service footprint, and repeated automated interaction may create load, trigger anti-abuse systems, or damage Netco's relationship with providers.

Netco therefore separates technical feasibility research from production-scale collection.

## Decision

Netco must not perform recurring, broad, or high-volume automated probing of provider coverage systems unless that provider integration has been explicitly approved for production collection.

The default policy is:

    one bounded probe
      -> confirmed technical understanding
      -> stop
      -> document
      -> decide later

A bounded probe may include a small number of requests needed to establish one of:

    positive understanding
    negative understanding
    confirmed ambiguity
    confirmed access barrier
    confirmed anti-automation boundary

Once one of those states is reached, automated exploration stops.

## What counts as a bounded probe

A bounded probe is intentionally narrow.

Allowed examples:

- open one public provider page once;
- identify whether an address checker exists;
- inspect the semantic controls required to operate it;
- observe one interaction flow;
- observe the network requests generated by that one flow;
- determine whether the flow depends on authentication, CAPTCHA, or another access boundary;
- determine whether a stable public API contract appears to exist.

The purpose is architecture discovery, not data acquisition.

## What is not allowed by default

Without a separate explicit decision, Netco must not:

- enumerate streets, buildings, entrances, or apartments;
- crawl coverage across neighborhoods or cities;
- continuously poll provider checker endpoints;
- parallelize checker requests;
- bypass CAPTCHA or anti-bot controls;
- impersonate users;
- create synthetic accounts to gain access;
- evade rate limits or blocking;
- rotate identities or infrastructure to avoid detection;
- infer a provider's full commercial footprint from systematic probing;
- treat undocumented internal endpoints as permission for bulk collection.

## Stop condition

Every provider probe must have a stop condition before it begins.

The default stop condition is:

    enough evidence to understand the integration boundary

Examples:

    checker is ordinary public form
    checker uses public GIS API
    checker requires authenticated session
    checker requires CAPTCHA
    checker does not expose address-level availability
    result state cannot be classified reliably

After the stop condition is reached, record the result and do not continue probing that provider until a new decision is made.

## Production collection approval

A provider adapter may move from research to production collection only after an explicit decision considering at least:

- provider terms and published usage expectations;
- technical rate limits and anti-abuse behavior;
- request volume;
- collection cadence;
- commercial sensitivity of the resulting dataset;
- whether provider cooperation or permission is appropriate;
- whether an official feed, API, partnership, or opt-in path exists;
- user benefit;
- operational and legal risk;
- ability to stop collection immediately.

Production approval should define a request budget and cadence.

## Time spreading

If production collection is later approved, Netco should prefer slow, distributed refresh rather than burst enumeration.

Examples:

    refresh stale evidence over hours or days
    prioritize user-relevant addresses
    avoid synchronized city-wide scans
    use per-provider request budgets
    stop on increased error/block rates

The purpose is freshness, not maximum extraction speed.

## Data minimization

Netco should collect the smallest amount of provider coverage evidence needed for the product question.

For example, if the product needs:

    provider X is orderable at building Y

Netco does not automatically need to discover every building provider X serves.

## Provider-specific research record

Every provider explored should have a small research record containing:

    provider
    date
    surface tested
    number/type of bounded interactions
    technical conclusion
    access boundaries
    whether further probing is paused
    next decision required

## Kyivstar bounded probe - 2026-09-25

A bounded technical probe was completed against the public Kyivstar Home Internet surface.

Observed interaction:

    Home Internet page
      -> semantic button "Перевірити адресу"

The probe established that the flow is not a simple static address form.

Observed supporting infrastructure included:

    silent OAuth flow
    invisible Google reCAPTCHA
    Kyivstar GIS requests

Observed GIS request paths included:

    /api-gis/locations
    /api-gis/countries
    /api-gis/cities/find-by-id/1

This is sufficient to understand the current integration boundary.

Decision:

    Kyivstar probing paused
    no enumeration
    no repeated address checks
    no endpoint exploration beyond this bounded probe
    no production collection

Any future Kyivstar work requires a new explicit decision.

## Relationship to VS6

RFC 0010 originally proposed Lanet + Kyivstar as the first two-provider proof.

This RFC narrows that plan.

The next implementation slice may build provider-agnostic, address-centric read contracts using already persisted data, but it must not require new provider probing.

Adding a second live provider adapter is deferred until the collection policy for that provider is explicitly approved.

## Invariants

1. Research is not production collection.
2. One bounded probe stops after a confirmed technical conclusion.
3. CAPTCHA and authentication are boundaries, not obstacles to bypass.
4. No provider-wide enumeration by default.
5. No repeated provider probing merely because automation is technically possible.
6. Provider-specific collection requires explicit approval.
7. Existing persisted evidence may be used without triggering new collection.
8. A read API must never trigger live provider probing.
